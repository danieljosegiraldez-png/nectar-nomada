# T12.5 — Photo/asset attachment across Traceability

**Sequenced before T13**, immediately after T12. No dependency runs either
direction between them; the ordering is about which risk matters more.
Photographs taken during a processing step are exactly the kind of physical
fact that cannot be reconstructed afterwards — the same reasoning ADR-039
records as its capability-versus-completion clause. A report can be built in
March. A photo of the drying beds in January cannot.

**Product owner decision, already made:** media is in scope, throughout —
harvest, receiving, processing, fermentation, drying, sampling — not only on
the lot report. The question this ticket answers is *what is the smallest
working photo path before harvest*, not whether to have one.

---

## 1. Scope

Six attachment points plus a Lot Detail section:

- Harvest, Receiving, Measurement, Fermentation (intervention and end),
  Drying (turn and end), Sample.
- A "Photos" section on Lot Detail, using the **renders-only-when-present**
  pattern T12 just established for Sensory — no empty section, no placeholder.

T10 is not reopened. This is a new numbered ticket, matching how T9.5 extended
T1–T9 rather than patching them retroactively.

## 2. Schema

**Nullable FKs per parent, not polymorphic.** `Asset` gains `lotId`,
`harvestEventId`, `measurementId`, `fermentationRunId`, `dryingRunId`,
`sampleId` — all nullable, all real FKs. ADR-020 decision 8 and `Measurement`'s
own schema comment both reject `subject_type`/`subject_id` pairs; the
never-built `ContentEntityLink` sketch from early planning is the polymorphic
alternative and should stay unbuilt.

**Provenance required from the start.** `Asset` currently carries none of
ADR-038's fields. A photograph is a fact-bearing record, so `provenanceClass`
is **required, no default** — matching T9.5's decision rather than repeating
the mistake it fixed. Add `sourceReference` and `dataQuality` per
`DATA_ARCHITECTURE.md` §4.

State the provenance class chosen per attachment point and why. A photo of a
drying bed taken at the bed is a `direct_observation`; a photo of a supplier's
spec sheet is a `manufacturer_spec`. These are not the same and the call site
knows which.

## 3. `creatorPersonId` — the same bug T9.5 fixed, caught before it ships

`finalizeAssetUpload` (`lib/partner/workspace.ts`) hardcodes
`creatorPersonId: userAccount.personId`. The field exists, is a real `Person`
FK, and structurally supports the observer-versus-uploader divergence — but no
code path can reach it. This is identical in shape to `operatorPersonId` before
T9.5: plumbing present, never exercised.

Fix it here rather than leaving it for an audit. Who took the photograph and
who uploaded it are different facts — a field technician photographs a
fermentation, the operator uploads it that evening. Default to the uploader's
Person (the common case, no extra tap), make it changeable.

## 4. Classification — choose deliberately

`lib/partner/workspace.ts` hardcodes `classification: "partner"` alongside
`partner:upload_media` and a partner-specific key prefix, so it is **not
reusable as-is**. A Traceability version needs its own service.

The classification default is a real decision with disclosure consequences, not
a copied constant. A photograph of a client's drying beds at a partner site is
not `public`, and getting this wrong leaks rather than merely degrading data
quality. Recommend a default with reasoning — `internal` is the likely answer —
and state how it interacts with `SPECIMEN_AND_MATERIAL_TRACEABILITY.md` §7's
client-site rule, where equipment and observations at a partner engagement carry
`classification = partner`.

Permission: reuse `lot:manage`, already the gate for every other write in this
module. No new permission — consistent with the whole T1–T9.5 pattern.

## 5. Offline — do not build it, do not preclude it

Photographs taken at a wet mill with no signal are precisely the case
`OFFLINE_FIELD_CAPABILITY.md` §6 specifies: structured data syncs first, media
follows, so the record exists before its attachments arrive.

This ticket does not build offline support. But the upload flow must not be
designed so that offline capture becomes impossible to add — specifically, a
record should not require its photo to exist before it can be saved. Note in
the implementation how a later offline path would attach.

## 6. UI

The client-side mechanics need no invention — `AssetUploadForm.tsx`'s
request → PUT → finalize flow is the pattern. One shared component wired into
six forms.

Field constraint: this gets used one-handed, outdoors, on a phone. Photo
attachment must never block saving the underlying record — a fermentation
measurement with no photo is a valid measurement. Attachment is additive, never
a required step.

## 7. Credentials — an operational blocker, state it plainly

R2 credentials (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
`R2_BUCKET`) do not exist in any environment. The adapter throws on first use.
This ticket's code can be written and unit-tested without them, but **it cannot
be live-verified**, and live verification against real data has been the
standard for every ticket in this phase.

Say clearly in the report what was verified and what could not be, rather than
reporting the ticket complete on a typecheck. If credentials are set before the
session ends, verify end to end: real upload, real R2 object, real `core.asset`
row, rendered on Lot Detail, then cleaned up.

## 8. Two T12 items to close in this session

Both are small and both concern a boundary that currently exists only as the
shape of a select statement.

**ADR-043** — record T12's decision to gate `getSensoryLinkageForSamples` on
`lot:view` rather than `blind_mapping:view`. The reasoning is sound and is
already in the plan doc, but it narrows a control that four separate documents
lean on as structurally guaranteed. A future session reading `RBAC.md` §7 and
then finding a function that reads `SensoryBlindMapping` under `lot:view` will
either flag it as a bug or treat it as licence to widen further. Record: what
was decided, why §7's purpose (protecting a judge from learning identity
*during* blind evaluation) is not what this touches, and the explicit limit —
aggregate score and session name only, never blind code, mapping row, or
evaluator identity.

**A test pinning that limit** — asserting `getSensoryLinkageForSamples` never
returns blind code, mapping ID, or evaluator identity. Right now a later
addition to the returned fields would leak through the one path that bypasses
`blind_mapping:view`, silently. `17_DESIGN_TO_IMPLEMENTATION_AUDIT_PROMPT.md`
Part A item 2 will check this claim; better it finds a test than a comment.

Also verify — and state — that the function is scoped to the requesting
operator's own lots. Leaf-scope containment via `lot:view` should handle it,
but this path is now special and the guarantee should be confirmed rather than
assumed.
