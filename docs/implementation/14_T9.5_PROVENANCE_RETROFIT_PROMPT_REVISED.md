# T9.5 (REVISED) — Provenance retrofit, completing what `5ceed23` started

**This supersedes the committed `14_T9.5_PROVENANCE_RETROFIT_PROMPT.md`.**
That version was written before we knew what `5ceed23` actually did, and it
contains one outright error (see §2). Commit this over it rather than
running both.

Do not begin T11 until this lands.

---

## 1. What `5ceed23` did, and what it left

**Done:** `sourceReference` exists on all five provenance-columned tables
(`LotTransformation`, `QuantityEvent`, `Measurement`, `HarvestEvent`,
`ReceivingEvent`). `provenanceClass` is threaded as a parameter through all
twelve write functions across the eight `lib/traceability/*.ts` files.

**Not done — and this is the whole point of the ticket:** every one of those
functions declares it as `provenanceClass?: ProvenanceClass` and resolves it
with `input.provenanceClass ?? "direct_observation"`. No caller anywhere
passes a value. `grep -c "provenanceClass" app/actions/traceability.ts`
returns zero.

So the plumbing exists and nothing uses it. Every row written to date —
including everything T10's eight new routes have produced — still asserts
`direct_observation` because nobody chose anything.

That is the condition this ticket exists to remove. `direct_observation` is
the strongest class in the vocabulary; a row falling through to it claims a
human directly observed something when in fact no claim was made at all.
`DATA_ARCHITECTURE.md` §4 requires unknown provenance to surface as
`data_quality = 'missing_source_record'`, never a sentinel — a default that
silently claims the strongest class is exactly that sentinel.

## 2. Correction: `recordedBy` does not exist and must not be created

The superseded prompt asked for a new `recordedBy` field. **That was a
mistake.** `operatorPersonId` already exists on the input interfaces in
`lots.ts`, `harvest.ts`, `measurements.ts`, `fermentation.ts`, `drying.ts`,
and `samples.ts`, is genuinely independent of `createdBy`, and does exactly
that job. Creating `recordedBy` alongside it would duplicate a field for no
reason — the specific failure this architecture is disciplined against.

**Use `operatorPersonId` throughout. Do not add `recordedBy`, `recordedAt`,
or any synonym.** `occurredAt` and `createdAt` already cover the timestamps.

The real gap is not the field — it is that no call site ever supplies it.
Every row currently has `operatorPersonId: null` and `createdBy = the
logged-in user`, so the divergence the schema supports is unreachable from
any UI.

## 3. Required changes

**(a) Decide required vs. nullable, and remove the fallbacks.** Recommend
one before implementing, with reasoning:

- **Required:** `provenanceClass: ProvenanceClass` (no `?`), every `??`
  removed, callers must choose. Strongest guarantee — the compiler enforces
  it and a future call site cannot silently fabricate a claim.
- **Nullable:** column becomes nullable, unknown provenance carried
  honestly as `data_quality = 'missing_source_record'` per
  `DATA_ARCHITECTURE.md` §4.

Either is acceptable. What is not acceptable is `?? "direct_observation"`
surviving anywhere.

**(b) Per-operation provenance at the call sites.** Removing the fallback
means every server action in `app/actions/traceability.ts` must pass a
value. These are not all the same, and choosing correctly per operation is
most of the work:

- A harvest weight read off a scale → `measured_fact`
- A lot merge or transformation → `original_record` of an action taken
- An operator's estimate entered from memory → neither of the above

State the class chosen for each call site and why. The choice belongs at
the action, where the operation's nature is known — never back in a service
default.

**(c) `operatorPersonId` must be reachable from the UI.** At minimum on
measurement entry, where the observer-versus-recorder distinction is real:
an operator entering a moisture reading a field technician took at the
drying beds. Default it to the logged-in user's Person — that is the common
case and shouldn't cost a tap — but make it changeable.

## 4. UX constraint, deliberately minimal

`16_ADAPTIVE_OPERATOR_WORKSPACE_PREAMBLE.md` §6 treats provenance capture
as a design question, and that research has not run. **Do not wait for it
and do not design a general solution here.** Build the minimum that stops
the silent default: sensible per-operation defaults chosen at the action
layer, plus an override on measurement entry for provenance class and
observer. Two taps maximum in the common path. Anything more ambitious waits
for the research.

## 5. Existing rows

Report how many rows currently carry the unchosen default, and whether they
are DEMO seed or real operator data. Recommend backfill, reclassification,
or leaving them — but do **not** rewrite existing rows to a different class
without stating the reasoning. Silently relabelling evidence is the same
error in the opposite direction.

## 6. Tests

At minimum: one asserting a write path cannot produce `direct_observation`
unless the caller chose it, and one asserting `operatorPersonId` and
`createdBy` can hold different people on the same row — the case that is
currently unreachable.
