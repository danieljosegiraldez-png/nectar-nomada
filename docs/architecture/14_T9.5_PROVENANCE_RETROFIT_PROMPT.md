# T9.5 — Provenance retrofit, before T10

**Why this is inserted here rather than scheduled later.** T10 is the first
operator UI — the first high-volume human write surface in the platform.
Every ticket after it adds call sites that would need the same correction,
and the verification pass already classified this cost as *compounding, not
one-slice*. Doing it now costs seven service files. Doing it after T14
costs those plus every form, action, and seed path built on top of them.

**Scope discipline:** this ticket covers the five Phase 1 traceability
tables only. The six tables named in `PHASE_1_TECHNICAL_EXECUTION_PLAN.md`
§6.3 (Assessment, AttributeResponse, PanelResult, CalibrationResult,
CompetitionResult, FieldSubmission) stay out of scope and remain a known
open item — do not expand into them here.

---

## 1. The actual problem

`provenanceClass` exists on `LotTransformation`, `QuantityEvent`,
`Measurement`, `HarvestEvent`, and `ReceivingEvent` as `NOT NULL` with
`@default(direct_observation)`. No service-layer write path in T1–T9 ever
sets it — `grep -rn "provenanceClass\|dataQuality" lib/traceability/*.ts`
returns nothing.

The consequence is worse than a missing field. Every row currently in those
tables **asserts that it is a direct observation**, whether or not anyone
observed anything. A null would be honest ignorance; a default that
silently claims the strongest provenance class in the vocabulary is the
system manufacturing an evidentiary claim at scale — in the one platform
whose central promise (`PLATFORM_OVERVIEW.md` §3, `DATA_ARCHITECTURE.md`
§4) is that it never does that. `DATA_ARCHITECTURE.md` §4 is explicit:
missing values get `data_quality = 'missing_source_record'`, never a
sentinel. A defaulted `direct_observation` is precisely the sentinel that
rule forbids.

Additionally, two of the four columns the plan's own §6.2 designed were
never added: `sourceReference` and `recordedById` / `recordedAt`.

## 2. Required changes

**Schema (one migration):** add `sourceReference` (text, nullable) and
`recordedById` (uuid, nullable, FK → `core.person`) plus `recordedAt`
(timestamptz, nullable) to all five tables, matching §6.2's design and
`DATA_ARCHITECTURE.md` §4's column set.

**`recordedBy` is not `createdBy`** — do not collapse them. `createdBy`
(already present, `DATA_ARCHITECTURE.md` §2) is the UserAccount that typed
the row into the system. `recordedBy` is the Person who actually made the
observation. These genuinely differ: an operator entering a moisture
reading a field technician took at the drying beds is one row with two
different humans behind it, and the whole point of the provenance model is
that the distinction survives. Nullable because it isn't always known —
but when it is known, it must be recordable.

**Remove `@default(direct_observation)`.** Decide and implement one of:

- (a) `provenanceClass` becomes a required argument at every write path —
  no default, the caller must choose. Strongest guarantee, most call-site
  churn.
- (b) The column becomes nullable, with `dataQuality =
  'missing_source_record'` carrying the honest "we don't know" state per
  `DATA_ARCHITECTURE.md` §4.

Recommend one with reasoning before implementing. The requirement is only
that the system stops asserting `direct_observation` for rows where nobody
chose it.

**Service layer:** update every write function in `lib/traceability/` —
`lots.ts`, `quantity.ts`, `measurements.ts`, `harvest.ts`,
`fermentation.ts`, `drying.ts`, `storage.ts` — to set provenance
explicitly. For each, state what the correct default *for that specific
operation* is and why. These are not all the same: a harvest weight
recorded at the scale is a `measured_fact`; a lot merge is an
`original_record` of an action taken; an operator's estimate entered from
memory is neither.

## 3. Existing rows

Report how many rows currently carry the silent default, and whether they
are DEMO seed data or real. Recommend backfill versus reclassification
versus leaving them — but do **not** rewrite existing rows to a different
provenance class without stating the reasoning, since silently relabelling
evidence is the same category of error this ticket exists to fix.

## 4. Tests

At minimum: one test asserting a write path cannot produce a row claiming
`direct_observation` unless the caller chose it, and one asserting
`recordedBy` and `createdBy` can hold different Person/UserAccount values
on the same row.

## 5. Deliverables

The migration, the service-layer changes, the tests, plus **draft ADR text**
(do not append) recording the retrofit, the (a)/(b) decision with reasoning,
the `recordedBy` vs `createdBy` distinction, the per-operation provenance
defaults chosen, and §6.3's six sensory tables as an explicit remaining open
item. Confirm the next ADR number against the live `DECISIONS.md`.

Also add the one-line note to `PHASE_1_TECHNICAL_EXECUTION_PLAN.md` §18
acknowledging `Sample.sourceLotId` as an intentional denormalization beyond
`COMMERCE_OPERATIONS_TOOLS_ARCHITECTURE.md` §F's minimal design — the
verification pass's only other finding, documentation-only, no code implied.

Do not begin T10 until this lands.
