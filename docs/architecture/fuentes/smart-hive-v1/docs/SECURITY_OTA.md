# Device identity, permissions, configuration and updates

V1 ships with cloud disabled. `rp2040-<unique_id hex>` is a hardware label, not a secret or authentication credential. Commissioning creates a random 128-bit epoch; never clone it to another deployment after a journal reset. Event ID combines device, epoch and monotonic sequence. Bind Pico ID, Notecard UID, owner/tenant, hive assignment history and hardware serial during authenticated commissioning. Never trust a tenant/hive supplied by a telemetry payload to grant access.

Notecard cellular connection is managed by Blues; Notehub route authentication and platform authorization are separate. Use HTTPS and a dedicated rotatable route bearer secret held in Notehub and the API secret store, never in firmware, QR code or browser. Validate the authenticated route's allowed project and Notecard UID against the registry. Redact tokens from logs. Rate-limit, cap payload sizes, validate schemas, reject conflicting duplicate IDs and retain audit events. Unknown devices enter a restricted enrollment queue.

User roles: owner/admin can enroll/reassign and manage sharing; operator can inspect/calibrate assigned hives; viewer can read explicitly shared measurements/manuals; researcher can export permitted pseudonymized study data. Every query and object-download link enforces tenant/resource permissions. Public build manuals may be public independently of private hive locations, videos and notes. Document retention/deletion policies and log privileged actions.

Physical access to RP2040 USB/flash is a trusted service boundary: this design does not provide tamper-resistant keys, secure boot or flash encryption. Protect service access mechanically; do not market the enclosure as tamper-proof. Camera footage should frame flowers/entrance and minimize incidental people; restrict originals and location metadata.

Current implementation: validated local JSON configuration via physical USB; no inbound remote command executor and no firmware OTA. Unknown keys/ranges fail validation. Preserve epoch and journal during routine service. Deploy in service mode, verify candidate file on host, back up logs/config, replace configuration, read back and reboot under supervision. Interrupted configuration replacement can require service recovery; it is not a transactional remote update system.

Firmware updates: verified release manifest plus known MicroPython UF2 and copied modules, physical access, logged operator/version and a retained known-good bundle. Never erase the filesystem before exporting unacknowledged logs. Test commissioning and rollback on a spare unit first. A SHA-256 manifest detects changes but is not a signature/authenticity system by itself.

Future OTA gate: add authenticated signed manifests, explicit hardware compatibility, power threshold, staged images/configuration, monotonic configuration versions, rollback after health-check failure, interruption tests and approved key rotation. RP2040 requires an evaluated boot/storage design for this; do not implement arbitrary Python downloaded from Notehub as OTA. Remote configuration should be a bounded allowlist with acknowledgement, replay protection and audit, independent of firmware updates. These are backlog requirements, not implemented features.
